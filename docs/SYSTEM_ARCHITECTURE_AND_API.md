# System Architecture, Modules and API Documentation

## 1. Project overview

**Project:** Smart AI Traffic Congestion Prediction and Reduction System Using Explainable Machine Learning and OpenStreetMap-Based Routing

The project is a Hyderabad-focused academic decision-support prototype. It combines a synthetic traffic dataset, multi-horizon congestion classification, model explanations, spatial hotspot analysis, anomaly screening, OpenStreetMap (OSM)-based route calculation, a FastAPI service and a Streamlit dashboard.

The current application works with historical records from **1 January 2025 to 31 December 2025**. It does not currently ingest a live traffic feed, control traffic signals, or measure real-world congestion reduction. Predictions and route outputs should therefore be presented as prototype decision-support results, not live navigation or proven traffic interventions.

## 3. Data layer

### 3.1 Source datasets

The synthetic dataset package contains five related tables:

| Dataset | Purpose |
|---|---|
| `road_segments.csv` | Road-segment identifiers and road/network attributes. |
| `traffic_data.csv` | Hourly traffic observations and traffic measurements. |
| `weather_data.csv` | Weather observations associated with the traffic timeline. |
| `accidents.csv` | Synthetic accident records associated with road segments and timestamps. |
| `events.csv` | Synthetic event records that may affect nearby traffic. |

The integrated machine-learning dataset is:

`data/final_dataset/ml_traffic_dataset.csv`

Recorded dataset scale: 60 road segments and 525,480 integrated hourly traffic records. The data are synthetic academic data, not a live sensor or government traffic feed.

### 3.2 Data target and classes

The base target field is `future_congestion_level`. It represents the next-hour congestion class in the integrated dataset. The five classes are:

1. Free Flow
2. Low
3. Moderate
4. High
5. Severe

For the multi-horizon pipeline, longer-horizon labels are generated by shifting the base target forward within each `road_segment_id`. The training implementation defines horizons of +1, +2, +3 and +6 hours.

### 3.3 OSM data

The route engine uses the locally stored Hyderabad drive graph:

- `data/osm/hyderabad_drive.graphml`
- `data/osm/hyderabad_drive.pkl`

The recorded graph contains 137,713 nodes and 357,965 edges. Project road segments are associated with OSM edges through the saved segment mapping. Traffic-aware edge costs are applied only when relevant mapped traffic observations are available; route results should expose/retain traffic coverage context.

## 4. Machine-learning pipeline

### 4.1 Training implementation

Primary training source:

`engine/multihorizon_forecaster.py`

The executable entry point trains the four horizons through `train_all_horizons()`.

Training stages:

1. Load and validate the integrated dataset.
2. Sort records by `road_segment_id` and timestamp.
3. Construct the target for the requested forecast horizon.
4. Remove target, identifiers and timestamp fields from the feature matrix as specified by the training code.
5. Create chronological training, validation and test partitions.
6. Fit numerical and categorical preprocessing using the training partition only.
7. Train an independent XGBoost classifier for each horizon.
8. Predict on the held-out test partition and calculate classification metrics.
9. Save the booster, preprocessing pipeline, label encoder and horizon metadata.
10. Save a combined summary in `multihorizon_summary.json`.

### 4.2 Preprocessing

The current training code uses:

- Median imputation for numerical columns.
- Most-frequent imputation for categorical columns.
- One-hot encoding for categorical columns with unknown-category handling.
- A separate fitted preprocessing pipeline for each horizon.

The reported transformed feature count is 117.

The current `build_model()` configuration in `engine/multihorizon_forecaster.py` is:

The following results were reproduced by executing the current training script and separately evaluating the saved models:

| Horizon | Accuracy | Balanced accuracy | Macro F1 | Weighted F1 |
|---|---:|---:|---:|---:|
| +1 hour | 63.60% | 48.52% | 48.33% | 61.82% |
| +2 hours | 63.66% | 48.89% | 49.32% | 62.10% |
| +3 hours | 63.53% | 49.06% | 48.71% | 61.86% |

These are classification metrics on held-out synthetic test records. They are not percentages of congestion removed, traffic reduced, or vehicles rerouted. ## 5. Analytics and intelligence modules

### 5.1 Prediction and forecasting

The prediction modules load saved model artifacts and apply the matching preprocessing pipeline before generating congestion-class predictions and class probabilities. Multi-horizon inference uses the independently saved models for +1h, +2h, +3h and +6h.

### 5.2 Explainable AI (SHAP)

SHAP is used to show feature contributions for selected predictions. These are post-hoc explanations of model output. They help users inspect which input features influenced a prediction; they do not establish causality or prove that changing a feature will reduce congestion.

### 5.3 Hotspot detection

The hotspot module groups geographically close project road segments using DBSCAN and summarizes traffic characteristics for the resulting groups. These clusters are analytical groupings, not official traffic zones or verified congestion boundaries.

### 5.4 Anomaly detection

The anomaly module combines Isolation Forest screening with a z-score rule to flag unusual records for review. Flags are indicators based on the available synthetic dataset; they are not confirmed real-world incidents.

### 5.5 OSM-based route optimization

The routing engine loads the Hyderabad road graph, maps route endpoints to graph nodes, and calculates routes using NetworkX graph search (including bidirectional Dijkstra in the implemented route workflow). Traffic-related edge penalties can influence route cost when mapped traffic observations are available. Outputs can include route geometry, distance, estimated travel time, average speed and traffic-data coverage.

A route with no mapped traffic coverage must not be described as validated traffic-aware navigation. The current project is a route-planning prototype, not a live navigation service.

### 5.6 Reports and decision support

The Reports module generates daily, weekly and anomaly summaries from the available dataset. The command-centre and reduction/recommendation components present analytical summaries and decision-support suggestions. They do not actuate traffic lights or execute traffic-management interventions.

### 5.7 AI assistant

The AI traffic assistant is an interface for asking questions about available project traffic and analytical results. Its answers are constrained by the data and functions connected in the current application; it should not be presented as an independent real-time traffic data provider.

## 10. Known scope and limitations

1. The traffic dataset is synthetic academic data covering 2025; it is not a live feed.
2. The reported test metrics measure congestion-class prediction on held-out synthetic records, not real-world traffic performance.
3. Class performance is uneven; the `Low` class has comparatively weak recall in the reported results.
4. SHAP feature contributions are explanatory, not causal.
5. Hotspot and anomaly outputs are analytical indicators, not verified events or official classifications.
6. Route traffic costs depend on the availability of mapped traffic observations. Some routes/timestamps may have zero traffic coverage.
7. The application does not control traffic signals, operate road infrastructure, or quantify real-world congestion reduction.
8. Independent validation using real traffic observations would be required before operational use.
